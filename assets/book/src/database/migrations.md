# Migrations, one table per file

```
migrations/
  sqlite/
    2026-01-01-000001_create_gateway_users/
      up.sql
      down.sql
    2026-01-01-000002_create_gateway_roles/
    2026-01-01-000003_create_gateway_permissions/
    2026-01-01-000004_create_gateway_role_permissions/
    2026-01-01-000005_create_gateway_user_roles/
  postgres/
    (the same five)
```

Every folder holds `up.sql`, which creates one table, and `down.sql`, which drops
it. One table per migration is a rule worth keeping: when something is wrong with
`gateway_roles` there is exactly one file to open.

## Why they are numbered

Diesel runs migrations in filename order, and the order matters:

```
000004_create_gateway_role_permissions
```

references both `gateway_roles` and `gateway_permissions`. Those tables must
exist first, so they are 2 and 3. Rename 000004 to 000001 and the migration fails
with a foreign key error against a table that does not exist yet.

The timestamp prefix is a Diesel convention. It sorts, and it does not collide
when two people add a migration in the same week.

## How Diesel knows what has run

It creates `__diesel_schema_migrations` itself and records a row per applied
migration. On startup `run_pending_migrations` compares that table against the
folders it was compiled with, and runs the difference.

Which means migrations are **append-only in practice**. Editing an `up.sql` that
has already run changes nothing — its version is already recorded. To change an
applied table, add a new migration.

## Embedded, not read from disk

```rust
pub const MIGRATIONS: EmbeddedMigrations = embed_migrations!("../migrations/sqlite");
```

`embed_migrations!` reads the SQL **at compile time** and bakes it into the
binary. The deployed program has no `migrations/` folder next to it and does not
need one.

The catch: change an `up.sql` and you must recompile before it takes effect.

## Seed data in migrations

Migrations 2, 3 and 4 do not only `CREATE TABLE` — they `INSERT`.

```sql
INSERT INTO gateway_roles (name, description) VALUES
    ('admin',  'Full access'),
    ('viewer', 'Read-only access');
```

So an `admin` role with every permission and a `viewer` role with the read-only
ones exist the moment the database does. There is something to log in as without
a separate seed script.

This is a judgement call, not a rule. Data that the application *needs* to
function belongs in a migration; data for testing does not.

## Adding a table

```bash
cargo install diesel_cli --no-default-features --features sqlite
diesel migration generate create_gateway_sessions --migration-dir migrations/sqlite
```

Write `up.sql` and `down.sql`, create the same folder under `migrations/postgres`,
then add a `diesel::table!` block to `models/src/schema.rs`.

`schema.rs` is checked in and edited by hand rather than generated by
`diesel print-schema`, because it has to describe both backends at once.

## Undoing one

```bash
diesel migration revert --migration-dir migrations/sqlite
```

Runs the newest `down.sql` and removes its row. This is why `down.sql` matters
even though nothing runs it automatically: it is what makes a migration
reversible while you are still developing it.
